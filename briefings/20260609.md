### 一、Anthropic 发布 Claude Fable 5（首个公开 Mythos-class 模型）+ Mythos 5（Project Glasswing 限定）+ GitHub Copilot 同步全 IDE 上架，Fable 5 必须显式开启且强制 30 天数据保留

1. 北京时间 2026-06-09，Anthropic 正式发布 **Claude Fable 5（`claude-fable-5`）**与 **Claude Mythos 5（`claude-mythos-5`）**，二者共用同一底层模型，差别仅在安全分类器：
   - **Fable 5** 是 Anthropic 第一次把 Mythos-class 模型向公众开放，定位"most demanding reasoning and long-horizon agentic work"，在 cybersecurity / biology / chemistry / model distillation 四类高风险域上有强制 refusal 行为，refusal 时 Messages API 返回 HTTP 200 + `stop_reason: "refusal"` + 明确标识哪个分类器拦截；refused 请求**不计费**，配合 `fallbacks` 参数（beta）或官方 SDK middleware（TS / Python / Go / Java / C#）可自动 fallback 到 Claude Opus 4.8 等其它模型，并以 **fallback credit** 抵免 prompt-cache 切换成本。
   - **Mythos 5** 同模型但去掉 cyber safeguards，仅对 **Project Glasswing 批准客户**（美国政府授权的网络防御 / 关键基础设施单位）开放，需通过 Anthropic / AWS / Google Cloud account team 申请；普通客户能拿到的就是 Fable 5。
   - 规格统一：**1M token 默认上下文 + 128K 输出**，定价 **$10 / MTok input、$50 / MTok output**（约为 Opus 4.8 的 2×）；**Adaptive thinking 始终开启**，不接受 `thinking: {"type": "disabled"}`，用 `effort` 参数控深度；**raw chain-of-thought 永不返回**（`thinking.display` 默认 `omitted`），如需可读思考过程必须显式 `display: "summarized"`；首发支持 **memory tool、task-budgets（beta header）、tool result clearing via context editing（beta header）、compaction、vision**。
   - **Covered Model 强制 30 天数据保留**：Fable 5 / Mythos 5 被设计成不支持 zero data retention，prompts 和 outputs 由 Anthropic 保留 30 天用于运行 safety classifiers，30 天后删除，且不用于训练。

### 二、GitHub 6/9 安全侧三件套：第三方编码 Agent 安全校验 GA（CodeQL + Advisory DB + Secret Scanning）+ 闲置仓库 30 天周期化代码扫描 GA—— Agent 治理边界从产品下沉到仓库

1. **Security validation for third-party coding agents（GA）** —— 北京时间 2026-06-09 GitHub changelog 发布（github.blog/changelog/2026-06-09-security-validation-for-third-party-coding-agents/）：当 **Claude、OpenAI Codex 等第三方编码 Agent** 直接在仓库内产出代码（实现功能、修 bug、补测试覆盖）时，GitHub 自动对其 PR 做与 Copilot cloud agent 同一条校验链：
   - **CodeQL** 静态分析潜在安全漏洞；
   - 新引入依赖**对 GitHub Advisory Database 查**恶意包广告与 CVSS High / Critical CVE；
   - **GitHub Secret Scanning** 检测 API key / token 等敏感信息；
   - 若发现问题，**agent 会在 finalize PR 之前自动尝试修复**（不是只报警）。
   该校验**默认开启**、跟随仓库已有 Copilot 设置，**不需要 GitHub Advanced Security license**；如果已经对 Copilot cloud agent 开了校验，第三方 agent 自动继承。GitHub 同时披露："since we released automatic code validation for Copilot cloud agent in **October 2025**, we've proactively prevented **hundreds of potential security leaks and vulnerabilities**"——这是 GitHub 第一次以官方口径给出 agent 安全校验的拦截量级。
2. **Periodic code scanning of inactive repositories（GA）** —— 同日发布（github.blog/changelog/2026-06-09-periodic-code-scanning-of-inactive-repositories/）：对 **6 个月没有 push 也没有 PR** 的"闲置仓库"启用**每 30 天自动周期化 code scanning**，仅对启用了 code scanning **default setup** 的仓库生效。开关在 **Settings → Advanced Security → Global Settings → "Keep scheduled scans running every 30 days for inactive repositories"**，组织级一次性开启。原先 code scanning 触发完全依赖 push / PR 事件，闲置仓库会"安全审计漂移"：依赖滚到了新的 CVE 但代码层从未重新扫过。
3. **配套补强**：① **Dependabot version updates 新增 Deno 生态支持**（github.blog/changelog/2026-06-09-dependabot-version-updates-now-support-the-deno-ecosystem/），只覆盖 version updates、不覆盖 security updates，配置在 `.github/dependabot.yml` 加 `Deno` 条目即可；② **GitHub Copilot 6/4 Enterprise Teams GA**（前期速递已展开）的延伸：6/8 同时把 **EMU 用户命名空间纳入 GitHub 原生 IP 白名单 GA**，覆盖 Web UI / Git 协议 / API 与 PAT / App token / SSH key 三类凭据。

为什么值得工程团队关注：① **agent 治理边界第一次明确"以仓库为单位"**——过去问题是"我们用 Copilot 就有校验、用 Claude / Codex 直连就没有"，今天起 *只要 agent 操作的是 GitHub 仓库*，都跑同一条 CodeQL + Advisory + Secret 校验，**agent 提供方变成可替换变量、安全策略变成仓库属性**。这是 6/2 Copilot SDK GA、6/4 Agent tasks REST API、6/9 Fable 5 上 Copilot 这条"多家 agent 共享同一 Copilot 入口"路径的最后一块拼图。② **闲置仓库 30 天周期扫描**是看似不起眼但治理意义明确的工程动作：依赖会自己漂、CVE 会自己出，过去这种仓库只能在 SCA / Dependabot 那侧看到，code scanning 侧是黑的；今天起所有 ≥ 6 个月闲置的 `default setup` 仓库都会被周期扫到，对 100+ 仓库的组织相当于一次性"补审计漏洞"。③ **Dependabot Deno 支持**填掉了过去靠手工脚本管 `deno.json` 的尴尬，让团队真正把 Deno-based service 当一等公民管。④ **EMU IP allow list GA** 是 Enterprise 治理侧的纯增量收紧，建议直接打开。

最可能影响的环节：流程 / 安全 / 仓库治理 / Agent harness。

### 三、npm v12 默认收紧三件套：`--allow-git`、`--allow-remote` 默认 `none`，`allowScripts` 默认关闭——v12 预计 7 月，今天起在 npm 11.16.0 以 warning 形式可提前演练

1. 北京时间 2026-06-09 GitHub changelog 发布（github.blog/changelog/2026-06-09-upcoming-breaking-changes-for-npm-v12/）：npm 下一个主版本 **v12** 预计 **2026 年 7 月**发布，**`npm install` 默认行为将出现三处 breaking change**，全部都是"原先自动执行、v12 起必须显式 opt-in"。所有变更**今天起在 npm 11.16.0+ 已以 warning 形式可观察**，团队可提前演练，不必等 v12 发布日。
2. **三处变更**：
   - **`--allow-git` 默认 `none`**：`npm install` **不再解析 Git 依赖**（直接 / 传递的都不行），除非显式 `--allow-git`。理由：Git 依赖里的 `.npmrc` 可以覆盖 git 可执行文件路径，即使加了 `--ignore-scripts` 也能形成代码执行路径。该变更 **2026-02-18 已预告**，在 **npm 11.10.0+** 可见 warning。
   - **`--allow-remote` 默认 `none`**：`npm install` **不再解析远程 URL 依赖**（如 https tarball、直接 / 传递的都算），除非显式 `--allow-remote`。`--allow-file` 与 `--allow-directory` 默认值在 v12 **不变**。该 flag 在 **npm 11.15.0+** 可用。
   - **`allowScripts` 默认 `off`**：`npm install` **不再执行依赖的 `preinstall` / `install` / `postinstall` 脚本**，除非在项目里显式 allowlist。关键：包**有 `binding.gyp` 但无显式 install 脚本时也会被拦**（因为 npm 会隐式跑 `node-gyp rebuild`），git / file / link 依赖的 `prepare` 脚本同样阻断。工具链：`npm approve-scripts --allow-scripts-pending` 看会被拦的包，`npm approve-scripts` 允许信任的、`npm deny-scripts` 拒绝，最终 allowlist 写入 `package.json` **必须 commit**。npm **11.16.0+** 已能看到对应 warning。
3. **upgrade path**：升级到 **npm 11.16.0+**，跑一次正常 `npm install`，看 warning 清单；用 `npm approve-scripts --allow-scripts-pending` 评估哪些包要 allowlist；commit 更新过的 `package.json`；v12 发布后未被 approve 的脚本就不会再跑。`npx` 与全局安装看 `allow-scripts config`。同日 changelog 还预告 **Dependabot 加 Deno 生态支持**（前条已述），两条共同构成 6/9 GitHub 在"包生态供应链"侧的一次明确表态。

为什么值得工程团队关注：① **npm install 默认行为变更是供应链风险面少见的"默认更安全"动作**——`allowScripts` 默认关闭意味着大量"安装时偷偷下载 / 编译 / 写本地文件"的供应链攻击路径在 v12 之后被默认阻断；但与此同时，**所有依赖 `postinstall` 自动产物（native build、playwright 浏览器、husky git hook 等）的工程链路必须显式 allowlist**，否则升级到 v12 后会"CI 红"。② **Git 与远程 URL 依赖默认拒绝**对内部 mono-repo / 私有库尤其重要：很多团队用 `git+ssh://` 直接装内部包，v12 后这一路径必须显式 `--allow-git`，对 CI Pipeline 与开发者本地都是 breaking。③ **接口前置 1 个月**（6/9 changelog 预告 → 7 月预计 GA）给团队留出明确的演练窗口；11.16.0+ 的 warning 是 dry-run 工具，建议在 **本周内**升上去先看 warning 清单。

最可能影响的环节：CI / Supply chain / 安全 / 开发环境 setup。

【工程意义】
- 对开发：本地 dev box 升到 npm 11.16.0+ 后，跑 `npm install` 会先看到 warning 而不是 error，需要主动梳理哪些包用 git+ 协议、哪些远程 URL tarball、哪些 `postinstall` 真的不能省（native build、headless browser 下载、git hook）——这些都要在 `package.json` allowlist 里显式标注并 commit。
- 对测试：在自家 CI 加一个"npm v12 dry-run"job：用 npm 11.16.0+ 在 `--audit=false` 下跑装 + 测，把 warning 数量与种类作为质量信号；同时跑一组"全部 deny scripts"的红线测试，看哪些 `node-gyp rebuild` / `husky install` / Playwright `postinstall` 会破坏构建，作为 v12 升级前必修清单。
- 对流程：① 安全 / 平台工程团队对内部模板仓库统一注入 npm 11.16.0+ 与 `npm approve-scripts` 流程，避免每个团队各自踩坑；② SaaS / 外发产品的 CI 流水线对 Git 依赖与远程 URL 依赖做白名单审查，提前与 v12 默认行为对齐；③ 把 `package.json` allowlist 字段纳入 PR review 默认关注项，不要无脑通过新增 allow 脚本的 PR。
