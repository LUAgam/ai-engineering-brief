### 一、Qwen3.7-Plus：阿里把"视觉 + 语言 + GUI/CLI + 代码"合到同一 Agent 基座，11 小时自治完成 App 全链路开发

1. 北京时间 2026-06-02 01:54（Qwen 官方账号 @Alibaba_Qwen 在 X 平台发帖时间；同日观点网 07:52 BJT、华尔街见闻 12:33 BJT、Alibaba Cloud Global LinkedIn 帖同步），阿里通义千问正式发布 Qwen3.7-Plus，定位为"将视觉与语言统一为一体化智能体基座"的多模态 Agent 模型，在 Qwen3.7 文本能力之上全面升级视觉-语言能力，同时保持编码、工具调用与生产力工作流的完整 Agent 能力。核心卖点是"多模态交互混合智能体"：可在同一 agent loop 内无缝混合 GUI 与 CLI 调度，能感知真实世界场景、读取屏幕并操作图形界面、基于视觉参考生成代码、端到端导航移动应用，并基于网络知识回答视觉问题；官方明确支持通过 Claude Code、OpenClaw、Qwen Code 等多种 agent harness 部署，跨 harness 表现稳定。
2. 官方给出的实测：基于 Qwen3.7-Plus 构建的 Hybrid-Agent 系统连续稳定运行 11 小时以上，触发 >1000 次工具调用、自主生成 >10000 行代码，无人工干预完成一款英语单词学习 App 的"需求分析 → 开发 → 测试 → 部署"全链路；另一案例是 Hybrid-Agent 自主对 macOS 原生 Stocks 应用做高保真复刻、保留原 dark theme 与交互。基准方面，官方披露 ScreenSpot Pro 屏幕理解 79 分，自报超过 GPT-5.4 与 Gemini-3.1 Pro；在 BabyVision、MathVision、AndroidWorld 等多模态高难度基准上相对前代显著跃升，Vision Arena 综合自评位列全球前五、中国第一。
3. 商业化形态：模型为闭源 / 商用专有，已上线阿里云百炼平台与 Qwen Studio，API 端点完全 OpenAI-compatible，并通过 Anthropic 协议调用；Vercel AI Gateway 同日（PT 6/1）已上架 `alibaba/qwen3.7-plus`，6/4 12:00 PT 前对付费用户免费。媒体披露定价 $0.4 / $1.6 per 1M tokens（输入/输出），约为 Qwen3.7-Max 的 40%；上下文 1M tokens，API 暴露 `preserve_thinking` 参数以避免长程任务中断时 reasoning 状态丢失。

最可能影响的环节：选型 / Agent harness / 测试 / 桌面 GUI 自动化。

【工程意义】
- 对开发：Qwen3.7-Plus API 完全 OpenAI 兼容，且原生支持 `preserve_thinking`，把"长程任务中途丢上下文 / cache 失效"这类已被 Anthropic Messages API mid-task system 条目部分解决的问题，在国产侧给了一条等价路径；可在不改 harness 的前提下，与 Claude Opus 4.8、GPT-5.5、Composer 2.5 做 1:1 抽样对比。

### 三、Anthropic Claude Code v2.1.160：shell startup / 构建配置文件写入需审批、`workflow` 触发词改名 `ultracode`（破坏式变更）

1. 北京时间 2026-06-02 10:10:17（GitHub Releases UTC 时间 02:10:17，作者 @ashwin-ant，anthropics/claude-code，130K stars，PyPI / 二进制同步发布），Anthropic 推送 Claude Code v2.1.160。这是 2.1 主线上的一次中等规模 patch，亮点集中在"写入审批面扩大 + 一个破坏式触发词改名 + 大量 background-session / Windows / WSL 修复"。
2. 写入审批面扩大：① 在写入 shell startup 文件（`.zshenv`、`.zlogin`、`.bash_login`）与 `~/.config/git/` 时新增 prompt，理由是这些路径可被用作命令注入与持久化入口；② `acceptEdits` 模式下，对一系列"配置即代码执行"的构建工具文件——`.npmrc`、`.yarnrc*`、`bunfig.toml`、`.bazelrc`、`.pre-commit-config.yaml`、`.devcontainer/` 等——不再无声放行，写入前必须经过审批。这两项都直接收敛了"Coding Agent 在 acceptEdits / Auto 模式下顺手改包管理 registry / 预提交 hook / devcontainer 配置导致供应链与持久化风险"的攻击面。
3. 其它工程相关变化：① **dynamic-workflow 触发词从 `workflow` 改名 `ultracode`，旧词不再触发任何 run，但自然语言要求"做一个 workflow"仍然可被识别**——这对已经在团队 prompt 模板、CI 脚本、内部 wrapper 里硬编码了 `workflow` 关键词的用户是破坏式变更；② 单文件 `grep`/`egrep`/`fgrep` 调用现在直接满足 read-before-edit 检查，省一次 Read；③ background session 修复一组重大体验 bug：完成态会话从 `claude agents` 恢复时丢失 chat history 并被重跑、隔夜 retired 的后台会话恢复后丢失对话并重跑、Windows 下后台会话目录无法被 `claude rm` 后立即删除、Esc / 方向键在 Windows 高负载下卡死、CJK IME 在 `claude agents` 视图中浮动到左下角等；④ Auto mode 分类器对常规动作的 reasoning 降低，减少 "could not evaluate this action" 阻塞；⑤ 在 Bedrock / Vertex / Foundry 第三方 provider 下 Auto mode 不可用时，提示语改为指向 `CLAUDE_CODE_ENABLE_AUTO_MODE` opt-in，不再误把锅扣到模型上；⑥ 环境变量 `CLAUDE_CODE_OPUS_4_6_FAST_MODE_OVERRIDE` 改为 no-op。

为什么值得工程团队关注：这是 Cursor 3.6 Auto-review（5/30）+ Codex CLI `/permissions`（5/28）之后，第三家头部 Coding Agent 在两周内明确收紧"写敏感配置 = 必须有人审批"的产品边界——意味着"Coding Agent 在 acceptEdits / Auto 模式下顺手改 `.npmrc` 引一个恶意源、改 `.pre-commit-config.yaml` 注入 hook、改 `.devcontainer/` 拿持久化"这条供应链入口在主流 IDE Agent 上正逐渐被堵；与此同时，`workflow → ultracode` 关键词改名是少数会让既有 prompt 模板/自动化脚本失效的破坏式变更，团队级 prompt 库需要扫一遍替换。

最可能影响的环节：开发 / 安全门禁 / 流程 / Agent 治理。

【工程意义】
- 对开发：日常 Claude Code 在 Auto / acceptEdits 模式下不会再无声改 `.zshenv`、`.npmrc`、`.bazelrc`、`.pre-commit-config.yaml`、`.devcontainer/` 等"配置即代码执行"路径；任何依赖 `workflow` 关键词触发 Dynamic Workflows 的内部 prompt 模板、CI 脚本、命令别名都需要替换为 `ultracode`，否则会"静默不触发"。
- 对测试：完成态后台 session 恢复丢历史/重跑、隔夜 retired session 恢复重跑这两类 bug 此前会污染 agent 评测的"是否完成同一任务"判断口径，2.1.160 修好后历史评测结果的可比性需要重新校准；同时 Auto mode 分类器在常规动作上降低推理，意味着此前 "could not evaluate" 阻塞造成的"任务失败"应该明显减少，可作为新 baseline 重跑一组评测看趋势。
- 对流程：把"Claude Code 在 acceptEdits 下能否写 `.npmrc`/`.bazelrc`/`.pre-commit-config.yaml`"纳入团队 onboarding checklist；并把 `workflow → ultracode` 改名作为"破坏式变更"邮件通知出去，覆盖 prompt 模板维护者、CI 脚本维护者、AGENTS.md 维护者，避免静默回归。

【建议动作】
- 立即可做：把团队所有 Claude Code 升级到 2.1.160，在 onboarding/工程内部文档里写明"Auto/acceptEdits 现在会拦截 shell startup / 构建配置写入"，并在仓库的 Claude Code 配置/prompt 模板里把 `workflow` 替换为 `ultracode`，跑一次 grep 自查。
- 本周可验证：在自家 SWE-Bench / Terminal-Bench / 内部 PR 评测集上重跑一组对照样本，对比 2.1.160 之前/之后的"Auto mode 阻塞次数"与"完成态后台 session 恢复成功率"，量化这次 patch 带来的端到端完成率变化；同时跑一组"恶意 `.npmrc` / `.pre-commit-config.yaml` 攻击 prompt"红队样本，验证新审批是否如期拦截。
- 暂时观察：Anthropic 是否会把 v2.1.160 的写入审批面进一步覆盖到 `.gitignore` / `.gitconfig` / IDE 配置等其它"配置即代码执行"路径；以及第三方 provider（Bedrock / Vertex / Foundry）下 Auto mode 何时正式开放对 Opus 4.7/4.8 之外的模型。

### 四、Anthropic 把 Project Glasswing 从 50 家扩到约 200 家：覆盖 15+ 国家关键基础设施、Mythos Preview 内部漏洞挖掘工具开放给"受信安全团队"按需申请

1. 北京时间 2026-06-02 22:44（TechCrunch 时间 7:44 AM PDT June 2；Anthropic 官方页 anthropic.com/news/expanding-project-glasswing 标注 Jun 2, 2026；CyberScoop / CNBC / Yahoo Finance / FT 同日跟进），Anthropic 宣布把 4 月 7 日 Project Glasswing 启动时的约 50 家初始伙伴，扩到再加约 150 家、合计约 200 家组织。新增组织来自 15+ 国家，覆盖此前未充分纳入的关键基础设施行业——电力、水务、医疗、通信、硬件——并明显加重"关键开源代码维护方"与"vendor（其代码库被大量其它机构与政府依赖的公司/非营利组织）"的比重。FT 援引知情人士披露的国别清单包含澳大利亚、加拿大、法国、德国、意大利、瑞士、荷兰、西班牙、比利时、瑞典、印度、日本、新西兰、韩国；CyberScoop 援引消息源称 Rubrik 也在本轮加入；既有伙伴中已公开的包括 AWS、Cisco、CrowdStrike、Google、JPMorganChase、Linux Foundation、Microsoft、NVIDIA、Palo Alto Networks 等。
2. 工程相关动作：① Anthropic 再次披露既有 Glasswing 伙伴用 Claude Mythos Preview 已经发现 >10,000 个 high/critical 级漏洞；② 同步推出 **Claude Security**——一款基于公开可用的 Claude Opus 4.8、扫描代码库并提交 patch 的产品，过去三周已用于打 patch 2,100+ 个漏洞；③ 这次扩容附带一条关键工程动作：**Anthropic 把内部为 Project Glasswing 伙伴开发的"漏洞挖掘工具"开放给"受信安全团队"按申请提供**（"on request, to trusted security teams"），即不再只是模型本身，而是把内部 harness/工具也外发；④ 后续将扩大 Cyber Verification Program，让更多组织在特定 cyberdefense 任务上拿到 Mythos-class 能力。
3. 节奏：Anthropic 自报"6–12 个月内多家厂商会有 Mythos 级模型，而很可能不带等量级安全护栏"；本次扩容以及"工具开放给受信安全团队 + Cyber Verification Program 扩大"是为这一时间窗做准备。值得注意的工程边界：Mythos 主模型本身不对外发布（"不会向通用市场开放"），开放的是基于 Opus 4.8 的 Claude Security 与内部 harness 工具。

为什么值得工程团队关注：对绝大多数 AI 应用工程团队，Mythos 本身仍然不可直接用，但今天有两个可立刻落地的信号：① Claude Security（基于已 GA 的 Opus 4.8）三周打 patch 2,100+ 个漏洞这一公开样本，给"用 Claude Opus 4.8 自动 scan + 自动 patch"这条路径提供了来自一方的工程基线，可直接拿来与 Claude Code 自家 PR 审批、Cursor Bugbot、Codex Security（OpenAI 端）做对照；② Mythos Preview 内部漏洞挖掘工具对"受信安全团队"开放申请这条窗口，意味着自建 AppSec / 安全审计平台的团队首次有了官方申请入口，而不是只能旁观。

最可能影响的环节：测试 / 安全门禁 / 流程 / 选型。

【工程意义】
- 对开发：把 Claude Security（Opus 4.8）的 scan + patch 工作流接进既有 PR 流，相当于在 IDE/CI 之外多了一条"独立 AI 安全审计"通路；与 Claude Code v2.1.160 当日新增的 build-config / shell-startup 写入审批组合，形成"agent 自身有写入门禁 + 外部 AI 扫描器同时巡查"的双层防护。
- 对测试：把 Claude Security 三周 2,100+ 漏洞这一公开数字作为自家 AppSec 工作流的对标基线，但要明确这是厂商自报口径、未独立复核；同时把"Mythos Preview 工具开放给受信安全团队"这条申请窗口纳入安全团队的供应商评估表，记录申请条件、SLA、可披露范围。
- 对流程：在选型与合规清单里区分清楚——Mythos 主模型仍不对外，Claude Security 是基于 Opus 4.8 的产品；Cyber Verification Program 是"按任务授权 Mythos-class 能力"的窄通路。三者权限粒度完全不同，不能等同看待。

【建议动作】
- 立即可做：让安全团队评估 Claude Security 是否作为内部 AppSec 工作流的第二审计通路，至少先在一个内部仓库跑 dry-run，对比 SWE-Bench Pro / 自家漏洞库已知样本上的召回率与 false positive。
- 本周可验证：把 Mythos Preview 工具开放给受信安全团队的申请窗口写进供应商评估表，明确"我们是否符合 trusted security team 条件、申请走哪条邮箱通路、可披露范围如何"。
- 暂时观察：Anthropic 是否会披露 Project Glasswing 第二批 150 家组织的具体清单（目前只给出行业与国别分布）；Mythos-class 模型公开发布的安全护栏是否在 6–12 个月内具备。
