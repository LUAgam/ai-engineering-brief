## 生成式AI

### 一、智谱开源 GLM-4.7：编程 SOTA 上线即开源，原生对接 Claude Code 等编程 Agent

1. 北京时间 5 月 25 日凌晨智谱发布并同步开源 GLM-4.7（zai-org/GLM-4.7），主打 Agentic Coding：SWE-bench Verified 73.8%（较 GLM-4.6 +5.8%，开源新高）、SWE-bench Multilingual 66.7%（+12.9%）、Terminal Bench 2.0 41.0%（+16.5%）、LiveCodeBench V6 84.9%；τ²-Bench 交互式工具调用 87.4 分超过 Claude Sonnet 4.5；BrowseComp 网页任务 67.5。模型可在 ModelScope（`ZhipuAI/GLM-4.7`）、Hugging Face、超算互联网 AI 社区下载，同时已上线智谱 MaaS 平台 bigmodel.cn / z.ai，OpenAI 兼容接口 endpoint 为 `https://open.bigmodel.cn/api/paas/v4/chat/completions`，模型名 `glm-4.7`，支持 `thinking: { type: "enabled" }`、`max_tokens` 可至 65536。
2. 工程侧关键变化是 GLM-4.7 在 Claude Code、TRAE、Kilo Code、Cline、Roo Code 等主流编程 Agent 框架中实现"先思考、再行动"机制——即模型显式输出计划-验证-执行的中间状态，便于 harness 拦截/审批；智谱在 Claude Code 环境下用 100 个真实编程任务（前后端 + 指令遵循）做了对比，相比 GLM-4.6 在稳定性与可交付性上有明显提升。
3. 商业化侧 GLM Coding Plan 维持最低 20 元/月起步包月，相比 Claude Pro 套餐对外宣称"3 倍用量"，并提供企业版套餐；GLM-4.7 同步登陆 Code Arena 全球盲测榜单，目前位列开源第一、国产第一。

为什么值得工程团队关注：这是当前最具"对得上 Claude Sonnet 4.5/Opus 4.7 编程能力 + MIT 友好开源 + 直接接入 Claude Code 工作流"三件套的国产编程模型，可作为对外 API 受限场景下的开源旗舰备选，也是评估"在自家 harness 里强制 plan-act 双阶段"的现成对照模型。

最可能影响的环节：选型 / 编码 Agent / 自托管推理 / 评测体系。

【工程意义】
- 对开发：让 Claude Code、Cline、Roo Code 等已经稳定的本地编码 harness，多了一个开源、价格远低于 Claude/GPT 的强模型选项；"先思考、再行动"对外暴露中间状态，team 可在 harness 里加白名单/黑名单约束 Agent 行为。
- 对测试：可在内部 SWE-bench Verified、Terminal Bench 2.0、内部回归套件上加跑 GLM-4.7，对照现有 Opus 4.7 / Composer 2.5 看真实代码任务的稳定性、tool calling 失败率；尤其 SWE-bench Multilingual +12.9 这一项值得多语种代码库重点验证。
- 对流程：开源权重可托管在内网，配合 vLLM / SGLang 进行私有化部署，对涉及敏感代码、合规要求高的团队是一条可落地路径；GLM Coding Plan 20 元包月也可以作为个人开发者的备份通道。

【建议动作】
- 立即可做：在 bigmodel.cn 申请 GLM-4.7 API key 跑一组真实任务横评（前端重构、后端 bug 修复、跨文件长链路改动），对照现役 Claude Opus 4.7 / Composer 2.5 / GLM-4.6 做主观体感与失败率对比。
- 本周可验证：把 GLM-4.7 接入团队的 Claude Code 或 Cline harness（OpenAI 兼容接口直接换 base_url 即可），用 5–10 个真实工单跑通"plan-act"模式，观察人为打断 plan 后的恢复行为。
- 暂时观察：Terminal Bench 2.0 41.0% 仍低于头部闭源；终端长链路任务（CI 修复、迁移类工单）建议在 GLM-4.7 上小流量灰度，不要直接替换主力。

### 二、xAI 发布 Grok Build CLI：终端编码 Agent + ACP，仅 SuperGrok / X Premium Plus 可用

1. xAI 官网发布 `Introducing Grok Build`（官方日期 2026-05-25，PT；按时区折算实际可能落在北京时间 5 月 25 日下午到 5 月 26 日凌晨，按官方日期收录）：Grok Build 是面向专业软件工程的终端编码 Agent + CLI，目前为早期 Beta，仅对 SuperGrok 与 X Premium Plus 订阅者开放；安装 `curl -fsSL https://x.ai/cli/install.sh | bash`，登录后即可在仓库目录运行 `grok` 进入交互 TUI。
2. 工程侧关键能力：① Plan 模式 `/plan` 可在执行前给出计划并支持逐步审批/重写，所有修改以 clean diff 呈现；② 原生兼容 `AGENTS.md`、plugins、hooks、skills、MCP servers，进入仓库自动接管现有约定；③ 大任务自动 dispatch 给"专门子 Agent"在独立 worktree 并行执行；④ 提供 headless `grok -p` 与 ACP（Agent Client Protocol）支持，可嵌入脚本、CI、其他 Agent 编排器。
3. 商业化与模型侧：底座为 Grok Build 0.1（`grok-build-0.1`），已通过 xAI Responses API 早期访问开放（`https://api.x.ai/v1/responses`），可直接用 Vercel AI SDK 等接入；订阅入口仍是 SuperGrok / X Premium Plus，第三方报道援引信息称起步定价 $99/月，并存在 SuperGrok Heavy 价格更高的更高档；模型与定价以 xAI 官方为准，第三方信息仍需追到一手。

为什么值得工程团队关注：这是 xAI 第一次把 Grok 真正以"专业开发用 CLI Agent + ACP"的形态推到终端，加上原生兼容 AGENTS.md / MCP 与 worktree 子 Agent，对已经在用 Claude Code / Codex / Cursor CLI 的团队，是一条直接的横向对比通道，但限定订阅与早期 Beta 让它更适合先做受控评估而不是全员铺开。

最可能影响的环节：开发 / 选型 / Agent harness 治理。

【工程意义】
- 对开发：使用 SuperGrok / X Premium Plus 的开发者多了一个与 Claude Code、Codex、Grok 模型亲缘度更高的终端 Agent；Plan 模式 + 子 Agent worktrees 是 Anthropic / OpenAI 生态外另一种成熟的"plan-then-act + 隔离执行"实现。
- 对测试：在 ACP 客户端（如 Zed）下 Grok Build 与 Claude Code、Copilot CLI 行为可对照评测，团队可在同一份评测集上加跑 grok-build-0.1，看 plan 通过率、destructive 操作发生率、token 成本。
- 对流程：早期 Beta + 订阅强绑定，意味着公司账号管理、密钥隔离需要先理清；按官方说明 OAuth 同意页可能显示 "Grok Build" 字样，但 OpenClaw、Hermes Agent 等开源 Agent 也会复用同一 OAuth client，需在内部沟通避免误解。

【建议动作】
- 立即可做：在受控环境内对 1–2 名开发者发放 SuperGrok / X Premium Plus 账号，安装 Grok Build，跑一周内部任务并记录 Plan 通过率、误操作率、token 用量；优先在 Plan 模式下使用，不开 Always-Approve。
- 本周可验证：在 ACP 兼容客户端中把 Grok Build 与 Claude Code 并行接入同一组任务，做"同任务双 Agent"对比；用 `grok -p` 把它接入一条简单的 CI 修复脚本，验证 headless 行为与重试能力。
- 暂时观察：Grok Build 0.1 仍是 0.1 版本；在生产侧大规模替换 Claude Code/Codex 之前等 1–2 个独立第三方 SWE-bench / Terminal-Bench 复测；定价与 SuperGrok Heavy 政策也需再观察一档。

【来源】
- xAI Newsroom：`Introducing Grok Build`（`https://x.ai/news/grok-build-cli`，2026-05-25）
- xAI Docs：`docs.x.ai/build/overview`、`docs.x.ai/build/modes-and-commands`
- 媒体报道（用于核对，非主来源）：Memeburn、Startup Fortune 关于 Grok Build / SuperGrok Heavy 定价的解读

### 四、富士通发布"自进化多 AI Agent"技术：把失败学习与策略改写做进多 Agent 协同闭环

1. 富士通官网（global.fujitsu/en-global/pr/news/2026/05/25-01）于 2026-05-25 在川崎发布 `Fujitsu develops self-evolving multi-AI agent technology that learns and adapts to business operations` 公告，提出一种允许多 AI Agent 作为"团队"协同工作并持续、安全地从日常执行结果、人类反馈、政策修订与规范变更中学习的多 Agent 技术。
2. 关键工程要点（基于富士通官方表述）：① 现有多 Agent 系统对单步指令处理较好，但无法独立分析失败原因并把改进安全地纳入后续操作；② 富士通方案让 Agent"自动验证操作经验"，识别失败原因并提取可执行知识，再以可控方式回写到 Prompt、检索方式、评估准则与运营规则；③ 目标是减少专家持续手工调 Prompt / 调评估 / 调路由的开销，让 Agent 在"业务规则不断变化"的真实企业环境中自我修正。
3. 公告未给出基准或论文，仅明确为"已开发的技术"，落地节奏与具体产品形态以富士通后续披露为准；属于工程方法论级别的研发信号，不是模型/产品发布。

为什么值得工程团队关注：在内部已经上多 Agent 的团队中，"失败学习 + 安全回写策略"这一闭环目前仍是 home-grown 各自实现，富士通把它显式提出并打成框架性叙事，是一份可参考的设计模板，特别是在"政策/规范变更频繁、专家维护成本高"的金融、电信、政务场景。

最可能影响的环节：流程 / Agent 平台 / 长期运维。

【工程意义】
- 对开发：在自家多 Agent 框架中划出 producing / verifying / done 等阶段，并在 verifier 后挂"失败原因抽取 → 策略更新"模块，是这一套思路的最小工程实现。
- 对测试：失败案例不只是触发告警或回滚，而是被作为"训练样本"喂回评估准则与 prompt；可以在评测套件中加上"经过 N 次失败迭代后，同类任务通过率是否上升"的纵向指标。
- 对流程：把"专家维护 Agent"显式作为一项可量化成本，是把多 Agent 项目从 PoC 推到生产的一条路径。

【建议动作】
- 立即可做：把富士通公告作为内部多 Agent 平台架构 Review 的一份参考资料，对照自家系统，标记"自动失败学习"、"策略回写"、"安全防护"三处当前缺失。
- 本周可验证：在 1 个具体场景（例如客服 Agent 团队）做最小闭环 PoC：失败任务 → 人工标注/Verifier 自动标注 → 自动改写 prompt 或路由表 → 跟踪同类任务上升曲线。
- 暂时观察：富士通后续是否给出基准、论文或开源参考实现；在没有数据前不要把"自进化"作为对外承诺。

【来源】
- Fujitsu Global：`Fujitsu develops self-evolving multi-AI agent technology that learns and adapts to business operations`（2026-05-25, Kawasaki, Japan）
