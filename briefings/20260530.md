## 工程工具链

### 一、Cursor 3.6 Auto-review Run Mode：Shell/MCP/Fetch 三段过审、`.cursor/permissions.json` 仓库级 autoRun 规则、官方 Agent Security 默认推荐

1. 北京时间 2026-05-30 08:04（Cursor 官方 Forum 帖时间 PT May 29, 5:04 PM，Cursor Changelog 标注 "3.6 May 29, 2026 · Auto-review Run Mode"），Cursor 推出 Auto-review 这一新的 Run Mode，作用范围限定 Shell / MCP / Fetch 三类工具调用：① 命中 terminal 或 MCP allowlist 立即放行；② 可沙盒化的调用进入 sandbox（macOS / Linux / Windows-via-WSL2，其它平台直接跳过到分类器，sandbox 启用网络与文件系统限制）；③ 其余调用统一交给 LLM 分类器子代理，结合当前请求与用户/仓库自定义指令，决定"放行 / 改换实现 / 升级到标准审批弹窗"三种结果之一；分类器调用计入既有 agent 用量、不额外计费。
2. 配置入口在 Settings > Cursor Settings > Agents > Run Mode；并新增仓库级 `.cursor/permissions.json` 的 `autoRun.allow_instructions` / `autoRun.block_instructions` 自然语言规则集，可直接 commit 进仓库由 team 共享，例如 "Block all npx commands" 与 "Block commands that create, edit, move, delete, chmod, chown, format, install, generate, or otherwise modify files outside the current project directory"。Cursor 官方 Agent Security 文档将 Auto-review 列为 Cursor 3.6 起的推荐默认；同时官方 Forum 与 docs 双方都明确：分类器为非确定性、可在两个方向出错，Auto-review 只是"best-effort 便利层"，不是 security boundary，对严格管控场景仍应使用 Allowlist + 手动审批 / Enterprise team admin 设置。
3. 媒体侧（Totalum、headsupai、Kingy）补充：3.6 同时给出 web 互动 demo "Auto-review 游戏"用于在不接入仓库前体验分类器决策；Sergey 等社区用户在 5/30 北京时间晚已开始反馈"建议提供 Auto-review without sandbox 选项"，间接说明 sandbox 误判存在；版本号 3.6 即在 Cursor 3 主线之上叠加 Auto-review 与若干稳定性修复，无 Composer 模型变化。

为什么值得工程团队关注：这是当前主流 Coding Agent IDE 第一次把"y 连点疲劳"问题以"Allowlist → Sandbox → 分类器"三段产品化，而且 autoRun 规则可以 commit 进仓库；对此前一直在外挂自家 hooks / wrapper / ClawHub 来约束 Cursor 工具权限的团队而言，意味着"权限策略代码化、可 review、可灰度"这一长期诉求第一次有了官方载体——但代价是分类器是 LLM 决定的非确定性环节，需要明确把它当便利层而不是合规边界。

最可能影响的环节：流程 / Agent 治理 / 安全门禁 / 选型。

【工程意义】
- 对开发：日常 Cursor agent 长跑会话被中断的次数会显著下降；同时 `.cursor/permissions.json` 让"哪些命令一律放行 / 哪些一律拦截"在仓库根目录就能写清楚，新人 onboarding 不再依赖口头约定或个人 Settings。
- 对测试：Auto-review 三档结果（allow / retry / classifier-approve）是天然的 agent 行为日志维度，可在内部接 hook 的方式拉取每条工具调用的"分流理由"，作为 agent 评测中"误放行率 / 误拦截率"两条新指标，与既有 SWE-Bench / Terminal-Bench 子集横向对照。
- 对流程：Run Mode 与 `.cursor/permissions.json` 让 IDE 侧 agent 行为可以纳入 Git-native 治理，PR 审批就能覆盖到"权限规则变化"这件事；但因为分类器非确定，安全/合规高敏场景仍应保留 Allowlist + 手动审批主线，而不是直接用 Auto-review 当默认。

【建议动作】
- 立即可做：在一个非关键仓库升级 Cursor 至 3.6，把 Auto-review 设为该仓库默认 Run Mode，并先 commit 一份最小 `.cursor/permissions.json`（典型的 block：`npx`、写入项目目录外的命令、删除 / 移动文件类命令；典型的 allow：read-only Shell、read-only MCP / WebFetch / WebSearch），观察 1–2 天的中断频率、误放行/误拦截案例。
- 本周可验证：在 agent 评测看板里为 Cursor 链路新增"Auto-review 分类决策日志"维度，对比同任务在 Allowlist-only / Sandbox-only / Auto-review 三档 Run Mode 下的端到端完成率、人工干预次数与异常工具调用比例，决定是否在 Enterprise 团队中切换默认 Run Mode。
- 暂时观察：Cursor 是否会按社区反馈提供"Auto-review without sandbox"选项；Auto-review 的分类器在多语种 / 内部 MCP 服务名出现时的误判率，以及 Agent 365 / 团队管理员策略与 `.cursor/permissions.json` 的优先级冲突如何收敛。

## 报告观点

### 三、OpenAI《A shared playbook for trustworthy third party evaluations》：第三方前沿模型评测应公开的 harness / token 预算 / 工具配置 / validity check 清单

1. 北京时间 2026-05-30 03:41（作者 Cedric Whitney 等人 X 发帖时间 PT May 29 12:41 PM；OpenAI 官方页 openai.com/index/trustworthy-third-party-evaluations-foundations/ 标注 May 29, 2026），OpenAI 联合 Cedric Whitney、Sandhini Agarwal、Esther Tetruashvili、Olivia Watkins、David Robinson 等人发布前沿 AI 第三方评测的"通用 playbook"，明确指出在 agentic 时代评测结果"不再只是模型本身决定的"，harness、tools、safeguards、控制循环、token / 计算预算、上下文都共同决定一项评测在测什么；建议第三方报告把评测拆成三类清晰命题：① 能力激发（capability elicitation）、② 安全机制表现（safeguard performance）、③ 与既有系统的对比（comparison），不再使用单一聚合分数。
2. playbook 给出可披露字段清单：模型版本、任务设定、计分方法、收集结果时的具体条件，以及"validity checks"——即评测者如何主动筛查 reward hacking、evaluation awareness（被评测模型识破 eval）、test-set 污染、refusals、sandbagging、broken problems，确认结果"survives reruns"而非一次性打中。OpenAI 同时援引两个具体数字佐证 harness 主导效应：① GPT-5.5 在 cyber-range 评测中开启 compaction 后表现明显抬升；② UK AISI 在把 token 预算从 10M 扩到 100M 后，相关评测最高出现 +59% 的成功率跃升——即 token 预算本身就是评测变量。
3. 报告同时指出未来标准化方向：与其追求"统一固定 harness"，更应允许定制化 harness 以暴露真实能力，但必须把 harness 限制写进报告；适配国家与国际层面的前沿 AI 评测与披露标准（如 California Transparency Act、EU AI Act、AISI 体系）需要的就是这一类"系统/激发方式/validity-check"细节。这是 OpenAI 继 5/28 PT《Frontier Governance Framework》之后第二份与第三方评测/披露直接相关的官方文档，定位偏"评测方法论"，不带具体新模型或新 benchmark 数据集。

为什么值得工程团队关注：这是来自前沿模型方的"我们希望第三方怎么评测我们"清单——对正在自建 agent eval、内部 SWE-Bench / Terminal-Bench / OSWorld 子集、或承担监管侧合规评测的团队，意味着可以把 OpenAI 列出的"模型版本 / 任务设定 / 工具配置 / token 预算 / 计分 / validity check"七个字段直接抄进自家 eval 报告模板。token 预算 +59% 的真实样本，则给"在做 agent 评测时遇到分数差 5–10pp 该不该信"这件事一个具体定量的提醒。

最可能影响的环节：测试 / 评测 / 流程 / 合规。

【工程意义】
- 对开发：自家 agent 报告里如果只写一个总分，对 GPT-5.5 / Opus 4.8 / Composer 2.5 / Step 3.7 Flash 这一档主流前沿模型几乎没有比较意义；按"能力激发 / 安全机制 / 对比"三类拆分能避免单一分数掩盖回归。
- 对测试：playbook 提到的 reward hacking / sandbagging / 污染 / refusals / broken problems 五类 validity check 完全可以写成 eval 平台的硬性 pre-flight 检查，对每次 benchmark 跑批前先验一遍，避免"分数高但不可重现"。
- 对流程：评测看板与 PR 评测产物里需要把 harness 配置、token 预算、工具集合作为强制元数据；UK AISI 那个 10M→100M token 预算 +59% 的样本可作为内部"评测可比性"培训案例，避免不同小组用不同预算跑出来的分数被直接拼到一张图上。

【建议动作】
- 立即可做：把 OpenAI playbook 列的 7 项披露字段（模型版本 / 任务设定 / 计分方法 / 工具与 harness 配置 / token 预算 / 上下文 / validity check 结果）做成一份内部 eval 报告模板，强制所有新评测必须填齐；对历史上未填齐的关键评测做一次回溯打标。
- 本周可验证：在自家 SWE-Bench / Terminal-Bench / OSWorld 子集上对同一模型跑两档 token 预算（如 10M vs 50M），观察是否复现"预算抬升带来 10pp+ 跃升"的现象；并选一个评测新增 reward hacking / contamination 的最小检查（例如随机替换问题中关键词后看分数是否异常稳定）。
- 暂时观察：OpenAI 这份 playbook 是否会与 California Transparency Act、EU AI Act、UK AISI 等监管侧实际报告标准对齐成统一格式；其它前沿厂商（Anthropic / Google / DeepSeek / Qwen / 智谱）是否给出对应版本的"我们希望被这样评测"文档。
