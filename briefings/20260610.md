### 一、GitHub Copilot 6/10 两条更新：Copilot Chat 直接看见并接力 cloud agent session（Session search + Get agent logs）+ Copilot CLI 实验性 `/security-review` 本地漏洞扫描

1. 北京时间 2026-06-10，GitHub 在 changelog 发布 **《Copilot Chat now sees your agent sessions》**（github.blog/changelog/2026-06-10-copilot-chat-now-sees-your-agent-sessions/）：在 web 端的 Copilot Chat 与 **Copilot cloud agent** 之间打通了 handoff 体验——
   - 当在 chat 里要求"开 session、提 PR、对某仓库做 deep research"时，**chat 会反映当前 session 状态**（进行中 / 完成）；session 完成后可直接在 chat 内追问该 session 或再起一个新 session。
   - 新增两个 chat 工具：① **Session search** —— 按 **topic / title / recency** 检索并摘要过去 agent session，"easy to pick up where previous work left off"；② **Get agent logs** —— 把 cloud agent 在某 PR 上的 **session 日志**拉进当前对话，可在 chat 里追问"改了什么 / 验证了什么 / 为什么"。两者本质都是把过去散落在 PR / session 列表的元信息变成 chat 可调用的检索 + 上下文 primitive。
2. 同日发布 **《Dedicated security review command now available in Copilot CLI》**（github.blog/changelog/2026-06-10-dedicated-security-review-command-now-available-in-copilot-cli/）：Copilot CLI 新增 **`/security-review` slash 命令（experimental，public preview）**，对当前本地代码变更做 **AI 驱动**的安全审查，返回 ① 按严重性 / 置信度评分的 high-confidence findings；② 可在 terminal 内直接 apply 的可执行修复建议。被调优用于发现**注入 / 跨站脚本（XSS）/ 不安全数据处理 / 路径穿越 / 弱加密**等"高频高影响"漏洞类。明确说明：**这是 Copilot 自己跑的扫描，不依赖 GitHub code scanning、Dependabot、secret scanning**，定位是"提交前轻量、按需"。启用方式：在 Copilot CLI 里开 experimental 模式，然后在任何项目里直接 `/security-review`。
3. **配套工程含义边界**：① Session search / Get agent logs 仅在 **github.com web 端 Copilot Chat** 落地，IDE 端（VS Code / JetBrains）暂未列入此次 changelog；② `/security-review` 仍是 experimental + on-demand，**不替代** code scanning / Dependabot / secret scanning，官方明确措辞是 "complement those tools by giving you a lightweight, on-demand way to review your changes before you commit"；③ 这两项与 6/4 GitHub Copilot 1M 上下文 + 可配置 reasoning、Agent tasks REST API 一起，构成"agent task → cloud agent 执行 → chat 内回顾 / 接力 → CLI 内 pre-commit 自查"的近端工作流闭环。

为什么值得工程团队关注：① **Session search / Get agent logs 是把 cloud agent 工作变成"团队可检索的工程记忆"的第一步**——以前 cloud agent 跑完一个 task，PR 自然成为记录，但 agent 的中间 session 日志与对话只能从 session 列表里翻；今天起这两个工具是 chat 一等内容，"过去某次 cloud agent 是怎么解决类似 bug 的"开始可以变成可复用的工程知识；② **`/security-review` 把"提交前安全自查"从 PR 审查阶段前移到 CLI**——团队此前依赖 CodeQL 在 PR 上跑得到反馈通常已经在 review 阶段，`/security-review` 是"我自己 commit 前先扫一遍"，对修复成本曲线是真实左移；但要注意它是 experimental 与 LLM-driven，false positive / 不全面问题需要团队预设期待，**不能拿它替代** GHAS / code scanning；③ 这两条都仍处于 preview / experimental，团队层应同步留意正式 GA 的兼容性。

最可能影响的环节：开发 / 代码评审 / 工程记忆 / 安全左移。

【工程意义】

### 二、GitHub CLI v2.94：`gh discussion` 一等命令族 + `gh issue` 直接管理 type / sub-issue / 依赖关系——把"agent 通过 gh 治理项目"从 raw `gh api` 提升到 first-class

1. 北京时间 2026-06-10，GitHub 同日发布两条 GitHub CLI 更新（均在 v2.94.0）：
   - **《List, view, and create discussions in GitHub CLI》**：新增 `gh discussion` 命令族，包括 `gh discussion list`（扫一个仓库最近 discussions）、`gh discussion view`（在 terminal 里读 discussion 与回复）、`gh discussion create`（开新 discussion）、`gh discussion edit`（更新 discussion）、`gh discussion comment`（评论）。Discussions 此前在 `gh` 内只能通过 raw `gh api` 调用，从今天起在 enabled Discussions 的任何仓库都可用。
   - **《Manage sub-issues, types, and dependencies from GitHub CLI》**：`gh issue` 直接暴露 ① **issue types**（create / edit 时设置类型，`gh issue list` 按类型过滤）；② **sub-issues**：`--parent` / `--set-parent` / `--remove-parent` 增删父子关系；③ **issue dependencies**：`--blocked-by` 与 `--blocking` 标记阻塞关系，并提供 `--add-*` / `--remove-*` 变体；④ `gh issue view` / `gh issue list` 新增 parent / sub-issue / type / dependency 的 JSON 字段，**自动化脚本可可靠读写 issue 结构**。
2. **官方明确目标用户**：原 changelog 措辞 "These are exactly the workflows that both developers, and **the coding agents that increasingly rely on `gh` as their interface to GitHub**, run every day"——即 GitHub 第一次把 `gh` 作为"coding agent 操作 GitHub 的标准接口"明确写进官方文档。Issue types 需要 organization 级别先定义。
3. **配套日期边界**：这两条 GitHub CLI 改进都是 **v2.94.0** 的一部分，团队需要安装或升级到该版本（`gh --version` 检查）；issue type 仅在已定义类型的 organization 内生效。

为什么值得工程团队关注：① **`gh` 一等化 = agent harness 简化**：原本要让 coding agent / cloud agent 创建 parent issue + sub-issue + 标记 blocking 关系，要么写一串 `gh api graphql` 调用，要么直接走 REST API；今天起 `gh issue create --parent N --blocked-by M --label X` 一条命令就能搞定，agent prompt 复杂度直接降一档；② **Discussions 终于成为 `gh` 一等公民**——Discussions 是很多开源项目实际沉淀的工程问答库，过去 agent / 工程师在 terminal 内访问它是个空白带，今天起 `gh discussion view` 可以直接在 CLI 内读完，对"agent 检索同仓库过往讨论作为修复线索"这一模式是直接可用的；③ **JSON 字段化**让"按 type 过滤 issue / 按依赖关系排序 / 找出当前 sprint 全部 blocked-by 的 leaf issue"等自动化脚本第一次有可靠数据源，不需要再脆弱地正则解析 markdown。

最可能影响的环节：流程自动化 / Agent harness / DevEx / 项目治理。

【工程意义】
- 对开发：使用 cloud agent 或本地 Coding Agent 的团队，可以把"以前需要打开浏览器调依赖关系 / 拆 sub-issue"的活，统一改成 `gh issue create/edit/list --type/--parent/--blocked-by/--blocking` 一行命令；把 `gh discussion {list,view,create,comment}` 加进开发者 cheatsheet。
- 对测试：把团队自家 agent harness 内"项目管理类"工具调用——创建 issue、拆 sub-issue、标记依赖——从 raw GitHub REST/GraphQL 替换为 `gh`，作为评测对照跑一遍，统计 ① 命令成功率、② 工具调用 token 节省、③ 失败原因（agent 是否仍偏向用 raw API）。
- 对流程：Project / Issue 治理团队可以重新审视"issue type 是否被 org 真正使用过"——`gh issue list --type bug/feature/...` 一旦在 CLI 易用，团队对 issue type 体系的实际利用率会上升；同时 `--blocked-by` / `--blocking` 给 sprint 复盘提供了一个可一行命令导出的"阻塞地图"，DevEx 可考虑搭一个看板。

【建议动作】
- 立即可做：在团队推荐工具版本里把 GitHub CLI 升到 **v2.94.0+**；在 agent harness 的 system prompt 或 tool definition 里，把"创建带 parent / 带依赖的 issue / 读 discussion"明确指向 `gh issue` / `gh discussion`，而不是 raw `gh api`。在 DevEx cheatsheet 加 5 行 `gh discussion` 与 4 行 `gh issue --parent/--blocked-by/--blocking` 示例。

### 三、Cursor Bugbot 切换到 Composer 2.5：90s ≪ 5min、bugs/review +10%、单次 cost −22% + `/review` `/review-bugbot` `/review-security` 把 PR 前的 Bugbot + Security Review 拉到本地

1. 北京时间 2026-06-10，Cursor 官方 changelog 发布 Bugbot 升级（cursor.com/changelog，Jun 10, 2026）：
   - **底模切到 Composer 2.5**：平均 review 时间从约 **5 分钟降至 ~90 秒**；平均每次 review 发现的 bug 数从 **0.56 → 0.62（+10%）**；**单次 run 成本下降 ~22%**。Bugbot 仍尊重 model block lists，速度与表现"may vary depending on your configuration"。
   - **`/review` 系列 slash 命令**：在 Cursor 3.7+ 与 cursor.com/agents 上，可在 push 之前直接以 `/review` 触发选择要跑的 agent（Bugbot / Security Review），或用 `/review-bugbot`、`/review-security` 直接调用对应 agent。**CLI 端支持随后跟进**。
   - **GitHub / GitLab 同步去重**：`/review` 会**与 GitHub 与 GitLab 上的 Bugbot 同步**——如果在本地跑过 `/review` 并随后开同 diff 的 PR，PR 侧 Bugbot 会识别到 diff 已审过，**跳过 review** 并留一条 comment 说明。
   - **增量评审**：可配置 Bugbot 只 review "**自上次 review 以来新增**"的变更，把 feedback 集中在最新差量。
2. **工程边界**：① 改动覆盖 Cursor 3.7+ 与 cursor.com/agents 两个入口，CLI "coming soon"；② Bugbot 与 Security Review 在 push 前本地跑的语义是"提前看一遍"，避免反复 push → PR → 等 review 的来回；③ 与 6/5 Bugbot AutoFix loop cap（同分支 push 触发的 Autofix 24h 内最多 3 次）形成"前端：push 前预审 + 后端：autofix 防失控"的双向收紧。
3. **可观测信号**：Bugbot 切到 Composer 2.5 后社区已有 capacity-exhausted 报错出现（forum.cursor.com，Jun 10 2:47pm "ERROR_RESOURCE_EXHAUSTED"），Cursor 官方回复定性为"temporary capacity shortage"，与 6/9-10 多次 Composer 2.5 容量波动一致；属于平台侧问题，不影响功能本身判定，但团队 SRE / Tech Lead 在评估"是否把 Bugbot 设为强 SLA 依赖"时需要计入。

为什么值得工程团队关注：① **5min → 90s 是从"PR review 阻塞"到"PR review 同步进行"的质变**——团队过去因为 Bugbot 慢而被迫在 PR pipeline 后端开 Bugbot 作为 nice-to-have，从今天起 Bugbot 完全可以放进 push 前的人机协同主路径；② **`/review` + GitHub/GitLab Bugbot 同 diff 去重**首次把"本地预审 + 远端 PR review"形成同一身份的 review 链，杜绝"本地刚跑完同一份 diff 远端又重复跑一次"带来的成本浪费；③ **增量评审**对"已 review 过、又来一次小改动"的常见 PR 反复迭代场景是直接节省。**注意成本测算口径**：Cursor 自报 "−22% per run"是 model-side 推理成本，不是用户最终 Cursor 计费——团队需自己复测包月 / usage-based 计费下的实际差额。

最可能影响的环节：代码评审 / Agent harness / FinOps / 开发者工作流。

【工程意义】
- 对开发：Cursor 3.7+ 用户今天起在 push 之前可以 `/review-bugbot` / `/review-security` 自检一次，避免"以为没问题、推上去 PR Bugbot 又挑刺"的回环；增量审查特别适合"已 review 过的 PR 又改了 3 个文件"的典型迭代。
- 对测试：在团队评测看板里跑一组对照——同样 50 个有真实 bug 的历史 PR replay，对比 ① 旧 Bugbot（Composer 2 / Sonnet 类）；② Composer 2.5 新 Bugbot；记录"完成 review 平均耗时、bug 召回率、误报率"。如果团队此前给 Bugbot 设过 P95 latency 5min 的 SLA，现在可以收紧到 P95 90s ~ 2min 这一档；同时把"Bugbot 已 review 过则远端跳过"的 diff hash 一致性作为去重正确性的回归测试。
- 对流程：把 `/review-bugbot` / `/review-security` 加进团队 push 前 SOP，并明确"必须在 push 前跑一次本地 review"的范围（如 main / release / hotfix 分支强制、feature 分支可选）；与 6/5 Autofix loop cap 形成 SOP：本地 `/review` → 本地 `/review` 修复 → push → 远端 Bugbot 自动跳过 → 仅在新增改动时再跑。

## 生成式AI

### 四、Google 开源 DiffusionGemma（26B-A4B MoE + 3.8B 活跃 + 文本扩散）：H100 1000+ tok/s、RTX 5090 700+ tok/s、量化 18GB VRAM、Apache 2.0、vLLM / Transformers / MLX / Unsloth Day-0 支持

1. 北京时间 2026-06-10，Google 在 `blog.google` 发布 **《Introducing DiffusionGemma》**（blog.google/innovation-and-ai/technology/developers-tools/diffusion-gemma-faster-text-generation/，Jun 10, 2026）：放出实验性开源模型 **DiffusionGemma**，建立在 Gemma 4 26B-A4B 骨干上、把"自回归生成头"替换为**文本扩散头**，**Apache 2.0**，weights 在 HuggingFace（`google/diffusiongemma-26B-A4B-it`）。
2. **关键指标**：
   - **26B MoE，3.8B 活跃参数**；**256K 上下文**；**140+ 语言**；**多模态输入**（text + image + video → text）。
   - **扩散解码**：从 256 token canvas 起步，每次 forward pass 并行 finalize **~15-20 个 token**；用 **bidirectional attention**（vs 自回归 causal），低置信 token 可被 **re-noise + 重生成**，实现"自我修正"；长序列用 **Block Autoregressive Diffusion**——256-token block 完全 denoise 后写入 KV cache，下一 block 以历史为条件再起 canvas。
   - **吞吐**：单 NVIDIA H100 **1000+ tok/s**；NVIDIA GeForce RTX 5090 **700+ tok/s**；量化（**NVFP4 4-bit floating-point**）后 **18GB VRAM 即可跑**，落入高端消费 GPU 区间。比同骨干自回归 Gemma 4 在 dedicated GPU 上**最多快 4×**。
   - **质量代价**：Google 明确说 **DiffusionGemma 在通用输出质量上低于标准 Gemma 4**，"For maximum quality production work, Google still recommends autoregressive Gemma 4"。
3. **生态支持**：vLLM Day-0（"the first diffusion LLM natively supported in vLLM"）、Hugging Face Transformers、MLX、Unsloth、NVIDIA NeMo（fine-tuning）；**llama.cpp 即将**；可在 Google Cloud Model Garden 或 NVIDIA NIM 上跑。Google 自己给了一个 **Sudoku** 微调案例——baseline 解题率约 0%，简单 JAX SFT 之后升到 80%，并且推理步数还降低，作为"约束生成场景上文本扩散的优势"的样例。
4. **适用 / 不适用**：官方给出明确边界——
   - **适用**：本地、低并发、交互式开发循环（inline editing、code infilling、非线性文本结构、约束生成、文档解析 / OCR、long-context 256K 文档分析）。
   - **不适用**：高 QPS 云端 serving——自回归在大 batch 下能把 compute 跑满，文本扩散并行解码收益递减，可能反而抬高 serving 成本。

为什么值得工程团队关注：① **解码瓶颈从"memory bandwidth"切到"compute"**：自回归在单用户低并发场景对 GPU 内存带宽极度饥饿、tensor core 大量闲置；DiffusionGemma 把 256 token canvas 并行 denoise，**让原本闲置的张量核心来干活**，本质是把"单用户单 GPU 本地推理"这条曲线第一次有效拉平。对自建 IDE 内置模型 / 本地 Copilot / 边缘部署的团队，这是一条**完全不依赖云端、单卡量化即可跑 1000+ tok/s** 的可选路径。② **Bidirectional attention + re-noise = 真正的 mid-generation self-correction**：自回归一旦写下 token 不能反悔，扩散可以撤销重写；对**代码 infilling、非线性文本结构、约束生成（Sudoku / 数学 / 蛋白质氨基酸 / 工程模板填空）**这类有内部一致性约束的任务有结构性优势。③ **Apache 2.0 + vLLM Day-0 + 量化 18GB**意味着 OSS 路径上"今天能跑"——不需要等社区做适配；④ **质量较 Gemma 4 低**这一点很关键——它**不是生产级通用替代**，而是**"以 4× 吞吐换部分通用质量"**的明确 trade-off，团队需要在自家任务上实测能不能 cover。

最可能影响的环节：本地推理 / 代码 infilling / 选型 / 推理成本结构。

【工程意义】
- 对开发：考虑过"在 IDE 内嵌一个本地补全 / 重构模型"的团队，DiffusionGemma 是少见的"单 H100 上即可 1000+ tok/s、量化 18GB VRAM 即可跑"的开源选项；对 inline editing / code infilling 场景特别适用，因为这本质是"在已有上下文里填中间 token"，正好是 bidirectional attention 的强项。
- 对测试：把自家 inline edit / completion / 约束生成评测集（如 SWE-Bench 的 fim 子集、内部代码模板填空集、Sudoku 等约束样本）在 ① 标准 Gemma 4 / Qwen-Coder / DeepSeek-Coder 类自回归 baseline；② DiffusionGemma 上各跑一遍，记录"完成率 / latency / tok/s / VRAM 峰值"四列。重点观察：自回归在该任务上是不是吞吐受限、扩散在质量上是不是可接受。**不要**直接拿它去跑通用 chat / 长文档总结类对照——Google 自己已经明确说这类任务上质量低于 Gemma 4。
- 对流程：本地推理 / 推理网关 / 边缘部署团队应把"扩散类 LLM"作为新一档候选纳入选型矩阵：架构上的差异（KV cache 行为、bidirectional attention、re-noise）意味着 latency / token billing / 并发模型与自回归不同，团队 FinOps 与 SRE 的容量规划口径要相应调整；不能把它当成自回归 Gemma 4 的 drop-in 替换。

【建议动作】
- 立即可做：让本地推理 / 推理网关团队 fork 一份 weights（`google/diffusiongemma-26B-A4B-it`），用 vLLM 在一张 H100 / 5090 上跑通基础推理；同步在内部 Confluence / Notion 写一页 "扩散类 LLM 选型笔记"（架构、吞吐、瓶颈、适用 / 不适用）。
- 本周可验证：在自家 inline edit / code infilling / 约束生成评测集（建议 30-100 题）上对 DiffusionGemma vs 现有自回归 baseline 做对照，重点跑：① 单 H100 / 5090 下 P50 / P95 tok/s；② 量化（NVFP4）前后质量；③ Sudoku / 工程模板填空类约束生成的完成率。把"是否值得在内部 IDE / inline editor 中嵌入"作为决策标准。
- 暂时观察：① 高 QPS / 大 batch 下的 serving 成本曲线（Google 自己提示"不适合高 QPS"，但具体 break-even 点在哪需要复测）；② llama.cpp 何时加入扩散支持；③ 后续是否会有更高质量版本能与标准 Gemma 4 拉平，从而真正变成 drop-in 替换；④ 其他厂商（OpenAI、Anthropic、Mistral、Qwen 等）是否会跟进文本扩散方向。
