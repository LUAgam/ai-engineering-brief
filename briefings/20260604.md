### 一、GitHub Copilot 全线开 1M token 上下文 + 可配置 reasoning：Claude Sonnet 4.6 / Opus 4.6-4.8、GPT-5.3-Codex / 5.4 / 5.5 在 VS Code、Copilot CLI、Copilot app 三个入口一并下放

1. 北京时间 2026-06-04，GitHub 在 changelog 上发布 **"Larger context windows and configurable reasoning levels for GitHub Copilot"**（github.blog/changelog/2026-06-04-larger-context-windows-and-configurable-reasoning-levels-for-github-copilot/）：今天起在 **VS Code、Copilot CLI、GitHub Copilot app** 三个入口同时打开 **1M token 上下文窗口**与**可配置 reasoning 级别**两项扩展能力。1M 上下文是与原有"默认上下文"并列的可选档，需要在模型选择器里手动切换；reasoning level 同样是可选下拉，可以"针对最难的架构 / debug 问题切到更高 effort"，也可以"对日常生成走默认级别"。官方明确："Choosing a larger context window or higher reasoning level will consume more AI credits per interaction. We recommend using the default context window and reasoning level for everyday tasks"。
2. 配套官方模型文档（docs.github.com/en/copilot/reference/ai-models/supported-models）列出当下两个扩展能力同时支持的模型矩阵，覆盖 **Claude Sonnet 4.6 / Opus 4.6 / Opus 4.6 fast mode (preview) / Opus 4.7 / Opus 4.8** 以及 **GPT-5.3-Codex / GPT-5.4 / GPT-5.5** 全线；并明确"目前 1M 上下文 + 可配置 reasoning 仅在 **VS Code 与 Copilot CLI** 可用，Copilot app 与其它 surface 后续陆续接入"，与 changelog 中的"expanding to more surfaces soon"对齐。
3. 同窗口 GitHub Copilot in VS Code 端 1.123（VS Code 1.123，PT 6/3 → BJT 6/4 凌晨）已经把 1M 上下文支持坐实在编辑器里（详见第四条），与 6/4 当天 changelog 形成闭环。GitHub 同日 changelog 还把"Agent tasks REST API public preview"（第二条主题之一）、"Fix with Copilot for failing Actions 进 Pro/Pro+/Max"、"Copilot Chat 接 PR 富上下文 GA"、"Enterprise Teams GA"、"GitHub Copilot in Visual Studio — May update"（含 Plan agent、Skills 面板、多文件 diff 总览）等一起发出。

为什么值得工程团队关注：1M token 上下文 + 可配置 reasoning 不是一项"新能力"，但首次以 *"GitHub Copilot 默认模型矩阵 + 三主入口"* 的形态下放——意味着团队过去为了让 Claude Opus 4.x 跑 1M 必须切到 Anthropic API 或 Cursor、为了拉满 GPT-5.5 reasoning 必须自己改 `reasoning_effort` 参数，今天起在 VS Code 模型选择器里直接是两个下拉；对应的代价是 AI credits 消耗按"扩展上下文 + 高 reasoning 双因子"叠加放大，团队层 FinOps 与 prompt 默认策略需要立刻同步。同时这一波"GitHub 一天放 6 条 changelog"事实上是 6/2 Build 2026 后 GitHub 把第一批 Copilot 平台动作落到正式 GA / public preview 的关键窗口（Copilot SDK GA、CLI 大版本 6/2，REST API / Fix-with-Copilot / PR 富上下文 / Enterprise Teams 6/4），值得作为一个时间段统筹治理。

### 二、GitHub 6/4 配套：Agent tasks REST API public preview + Fix-with-Copilot for failing Actions 进 Pro/Pro+/Max + Copilot Chat 接 PR 富上下文 GA + Enterprise Teams GA

1. **Agent tasks REST API（public preview）** —— Copilot **Pro、Pro+、Max** 用户今天起可通过 REST API **以编程方式启动并跟踪 Copilot cloud agent 任务**。典型用例：在 CI、内部平台或自定义工作流里"一键派任务给云端 Copilot agent"，比如"全仓库重构 / 给某 PR 跑修复 / 周末批量更新 release notes"。鉴权支持 personal access token（classic 与 fine-grained）以及 OAuth token，文档入口 `agent tasks REST API documentation`。这是把 6/2 Copilot SDK GA 之后 cloud agent 这条路径"完全可程序化"的关键拼图，原先 Pro 用户只能在 GitHub UI 里点按钮派任务。
2. **Fix with Copilot for failing Actions（Jun 4）** —— GitHub Actions 工作流 run 失败页面的 "Fix with Copilot" 按钮今天起对 **Copilot Pro、Pro+、Max** 个人用户开放（原先仅 Business / Enterprise）。点一次按钮，Copilot cloud agent 会在它自己的云端开发环境里调查失败原因、push fix 到当前分支、并 @ 你 review；典型场景是 lint 失败 / 单测失败 / 依赖版本不兼容等"耗时但机械"的修复，把"工程师手动看 log → 本地复现 → 提 fix"压缩到"点按钮 → 等 cloud agent 跑完 → review PR"。
3. **Copilot Chat 接 PR 富上下文（Jun 4 GA）** —— github.com 上的 Copilot Chat 在打开 diff / PR 页时，**自动把 file changes、commits、comments、reviews** 拉进上下文，并支持"在 diff 顶部 'Ask about this diff' / 顶栏 Copilot 按钮 / 选中代码段右键调起 chat"三种入口；同窗口对话与 PR 对话面板并列，无需在标签页之间来回切。该能力已从 4/23 的 public preview 转为 **GA、对所有 Copilot license 开放**。
4. **Enterprise Teams（Jun 4 GA）** —— GitHub Enterprise Cloud 的 **Enterprise Teams** 从 2025/09 public preview 转为 GA：admin 在 enterprise 级别一次性定义 user group，可在 enterprise 下所有 organization 之间统一指派角色，不再需要每个 org 重复创建同名 team；REST API 同步可用（`GET/POST/PUT/DELETE /enterprises/{enterprise}/teams[/{team_slug}]`），endpoint 接受 classic PAT 的 `read:enterprise` / `admin:enterprise` scope，但目前**不支持 fine-grained PAT 与 GitHub App token**。

为什么值得工程团队关注：① Agent tasks REST API + Fix-with-Copilot 把"Copilot cloud agent 不再是 Copilot UI 限定行为"——CI 系统、内部 portal、运维机器人都可以编程式派 agent 任务，事实上等价于一条新的"GitHub 内部 RPA / 自动化 worker 协议"；② Copilot Chat PR 富上下文 GA 意味着团队在 GitHub PR 界面进行 review 时，"Copilot 是否真的看到了该 PR 的 commits / comments / 既往 review"从此前 preview 期的"看运气"变成 GA 兜底；③ Enterprise Teams 把"多 org enterprise 团队成员管理"从"每个 org 各自维护一份 team"收敛到 enterprise 单点，对 100+ 仓库 / 多子公司结构的大型组织是治理层一次真实简化，但要注意 fine-grained PAT 与 GitHub App token 暂不支持，自动化脚本接入需要先确认 classic PAT 是否仍合规。

最可能影响的环节：流程自动化 / CI / 代码评审 / 权限治理。

【工程意义】
- 对开发：Pro/Pro+/Max 个人用户今天起可以在 Actions failure 页直接让 Copilot cloud agent 修；建议团队定一条规范："仅在简单 lint / 单测 / 依赖错配类失败上点 Fix with Copilot，不要在涉及业务逻辑或安全 / 鉴权变更的失败上让它自动 push"。Agent tasks REST API 适合包成内部 CLI（如 `inner-tool copilot-cloud-task --repo X --prompt Y`）方便团队成员复用，而不是每人各自写 curl。

## 生成式AI

### 三、Cursor 3.7：Canvas Design Mode（点选标注 UI 元素引导 agent 编辑）+ Context Usage Report（agent 上下文消耗交互式分解）

1. 北京时间 2026-06-04，Cursor 发布 **3.7**（cursor.com/changelog，Jun 4, 2026），围绕 5/20 起加入的 canvases（agent 产出的可交互 artifact，如 dashboard、report、内部工具）做两项关键扩展：
   - **Design Mode in canvases**：在 canvas 内可像在浏览器一样**直接选中并标注 UI 元素**，给 Cursor agent 提供"指给它看"的修改指令，不再需要用文字描述（如"把右上角第三个按钮往左挪 12px、改成 primary 颜色"），可在 canvas 上点 + 注释 + 多轮迭代。
   - **Context usage report in canvas**：Cursor 可把 agent 当前的**上下文消耗作为一个可交互 canvas** 输出——context explorer 把 token 按 **system prompt / tool definitions / rules / skills 等维度**拆分，因为是 canvas，可在画布里继续追问 agent；canvas 内嵌的 **"Debug with Agent"** 按钮直接打开新对话，让 agent 在新会话里找减少 context 使用的优化点。
2. 同窗口 canvas 系统的 4 项相关改进：① shared canvas 可在浏览器**全屏打开**便于演示；② agent 可以**在 canvas 里嵌入按钮**，点击会触发一个固定 prompt（等价于"画布内的小机器人"）；③ agent 修复 canvas 类型错误的能力提升；④ component 样式与 chart 自定义能力增强。
3. 工程相关边界：3.7 本身延续 6/3 GA 的 Cursor Enterprise organizations 治理层（详见 6/3 速递），Design Mode + Context usage report 与 Composer 2.5、Auto-review 等存量能力组合使用；canvases 在 Pro、Teams、Enterprise 三档可用，未给出新计费档位。

为什么值得工程团队关注：① **Design Mode 把"agent 改 UI"从"对话→改→看效果→再对话"的回环缩短为"画布上指给它看"**，对内部 dashboard / 临时审批面板 / 客户演示用的 prototype 是真实的工时节省，路径上等价于"轻量版 Figma → Code"但在 agent 侧闭环；② **Context usage report 是少见的"把 agent context budget 当一等公民暴露出来"的 IDE 能力**，对"我们的 agent 为什么这次推理这么贵 / 为什么 context window 总是被 system prompt + rules 吃掉一半"这类调试，把"团队自己拉 token usage 表"的工作下沉到 IDE；③ 配合 OpenAI Codex Sites（6/3 速递主条目）、GitHub Copilot 1M 上下文（本期第一条），团队"内部工具 / dashboard / 上下文治理"这条线在 6/2-4 三天内被三家厂商以非常一致的方向推动。

最可能影响的环节：开发 / 内部工具 / Prompt / 成本治理。

【工程意义】
- 对开发：当 agent 产出的 canvas 是 dashboard / 内部工具 / 报告类时，Design Mode 把"我想改这一块"从"语言描述"变成"点选 + 标注"；建议在使用 canvas 的团队层规范里加一条"UI 调整请优先使用 Design Mode 而非纯文字描述"，以减少 agent 误读和无效迭代。
- 对测试：Context usage report 把 agent context 拆成 system prompt / tool definitions / rules / skills 等维度——可以在跑回归评测前先用它对当前 agent harness 做一次"上下文体检"，识别"哪些 skills / rules 占了 30%+ token 但回报很低"，作为评测元数据的一部分纳入分析。
- 对流程：canvas 内嵌按钮 + Debug with Agent 把"日常运维型小操作"做成"画布上点按钮触发固定 prompt"模式；建议平台工程团队评估"是否把内部 runbook / oncall 操作面板从 Slack 命令搬一部分到 canvas + 嵌入按钮"，与 OpenAI Codex Sites 形成本地 IDE 与云端托管两条候选路径对照。

### 四、VS Code 1.123：Anthropic / OpenAI 1M token 上下文 IDE 端落地 + chat session 自动跨机同步 + Agents window 多 session 并列 + `/research` 命令进 Copilot CLI Insiders

1. **发布时间**：VS Code 1.123 release date 为美西 2026-06-03（PT 6/3 → BJT 6/4 凌晨），同窗口 GitHub Changelog 6/3 发布《GitHub Copilot in Visual Studio Code, May releases》对 v1.120-v1.123 做 May 月度汇总；6/4 GitHub Copilot "1M 上下文 + 可配置 reasoning"主 changelog（本期第一条）正好以 VS Code 1.123 作为编辑器端的承接版本。
2. **五个主要更新**（按 release notes 顺序）：
   - **Larger context windows**：Anthropic（Claude Sonnet / Opus 系列）与 OpenAI（GPT-5.x）模型在 VS Code 内支持 **1M token 上下文**，与 GitHub Copilot 6/4 changelog 给出的模型矩阵一致。
   - **Session sync**：chat sessions 现可**自动同步到 GitHub 账号**，跨机器 / 跨 workspace 形成个人级、可全局搜索的编码历史。开启方式：`chat.sessionSync.enabled`；Copilot 状态栏可看同步状态。
   - **Agents window**：可**并列打开多个 agent session**，方便对比或并行 review 工作。
   - **Research agent (preview)**：在 **Copilot CLI 本地 session（Insiders）** 中输入 `/research <topic>`，agent 会对该主题在仓库代码、相关 GitHub 仓库与公网上做深度调研，输出 **带充分引用的 Markdown 报告**。
   - **Integrated browser updates**：内嵌浏览器支持 favorite pages、扩展更多 screenshot 捕获选项。
3. **配套小变更**：新发布的非可信发布者扩展版本会**延迟 2 小时**才自动安装（Microsoft / GitHub / OpenAI 等 trusted publisher 例外），算是供应链侧一次缓冲；Agents 模块新增 `/chronicle` 命令、sandbox 在网络相关命令上加入 retry。

为什么值得工程团队关注：① **VS Code 是 GitHub Copilot 1M token 上下文落地的第一线**——团队升级到 1.123 之前，"1M 上下文"在 VS Code 内是说不通的；升级后才真正可以在模型选择器里切；② **Session sync 把"我在公司机器开过的 Copilot 对话 / agent 任务"自动同步到 GitHub 账号**，对在公司机器 + 笔记本 + 居家三处办公的工程师有真实价值，但同时把"agent 对话历史"变成必须治理的数据——团队应在 IT 政策里明确是否允许这条同步打开，以及 enterprise admin 是否需要 audit 这部分历史；③ **`/research` Copilot CLI Insiders preview** 是 GitHub / VS Code 第一次给 IDE 内置 "deep research agent"，对工程师"理解陌生代码 / 调研 lib API / 比较多种实现方案"的场景，从"自己开浏览器看 SO + GitHub Issue"压缩到 CLI 一条命令；④ 非可信发布者扩展 **2 小时自动安装延迟**是供应链侧少见的 default behavior 变化——对"恶意扩展上架 → 大量员工被静默更新"这条攻击路径是一次有效缓冲。

最可能影响的环节：开发 / 安全 / 数据治理 / 研究调研。

【工程意义】
- 对开发：1M 上下文要真正可用必须升 1.123；建议团队 IT 把 1.123 列为推荐版本，并在内部说明文档中明确"1M 上下文按需开启、AI credits 消耗显著放大"。Research agent 在 CLI Insiders preview 阶段适合自愿 early adopter 使用，不要在生产 CI 链路上直接接入。
- 对测试：建议把"启用 session sync 前后 agent 上下文复现度"作为 IDE 侧回归项——理论上同步好处是跨机器拿到一致历史，但实际可能因网络 / 同步延迟导致两台机器看到的 session 不一致，这种场景在编程对答中容易引发"agent 不记得我们说过的事"投诉。Research agent 输出的 Markdown 报告本身可以作为评估目标，跑一组"对同一陌生 lib 用 `/research` vs 手工调研"的对照，看引用准确率与覆盖率。
- 对流程：Session sync 必须配合数据治理一起出策略；建议 IT / 安全团队在打开 `chat.sessionSync.enabled` 默认值前先答两个问题——"是否允许 Copilot chat 内容跨机器同步到员工 GitHub 个人账号？""enterprise admin 是否有审计 / 暂停 / 导出能力？"。Extension 2 小时安装延迟则是默认更安全的方向，可以保留默认行为。
